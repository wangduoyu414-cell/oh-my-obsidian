## 1. 存储层

项目根目录可以直接作为 Obsidian Vault 或普通文件工作区使用。Obsidian 只承担人类阅读、链接、检索和派生视图；核心事实、规则和工作状态必须保存在可移植文件中，不依赖特定插件或本地缓存。

| 路径 | 权威内容 | 默认写入者 |
|---|---|---|
| `00-Inbox/` | 未登记材料 | 人工或受控导入 |
| `10-Sources/assets/` | 只读原始来源 | 归档操作 |
| `10-Sources/notes/` | 来源解释、证据定位、处理状态 | 核心工作流 |
| `20-Knowledge/objects/` | 经审核的对象当前视图和历史 | 已批准更新流程 |
| `20-Knowledge/topics/` | 可重复消费的稳定主题知识 | 已批准更新流程 |
| `30-Work/change-proposals/` | 未批准变更 | 核心工作流 |
| `30-Work/context-packs/` | 任务受控上下文 | 核心工作流 |
| `30-Work/tasks/` | 工作状态和完成证据 | 人工或受控工作流 |
| `40-Outputs/drafts/` | 未审核产物 | 产物生成流程 |
| `40-Outputs/reviewed/` | 已内容审核产物 | 审核流程 |
| `40-Outputs/final/` | 明确批准版本 | 授权发布流程 |
| `90-Archive/` | 关闭、替代或转存内容 | 归档流程 |
| `_System/` | 工作流规范和工具 | 项目维护流程 |

## 2. 写入边界

- 原始来源可以从 Inbox 移入来源资产目录，但内容不得修改。
- 来源笔记不得冒充对象当前知识。
- 变更建议不得被普通检索当作已批准事实。
- 上下文包不得回写对象事实。
- 草稿不得进入最终目录。
- `_System/` 不保存任务事实、来源摘要或正式产物。

## 3. 来源笔记

来源笔记的单位是逻辑数据集，而不是固定的物理文件。

一份来源笔记至少说明：

- 对应资产及内部定位；
- 逻辑数据集边界；
- 来源角色；
- 时间和适用范围；
- 识别到的对象、断言、事件、关系和事项；
- 冲突、缺失和质量标记；
- 建议更新对象；
- 处理版本和审核状态。

来源笔记原则上保持稳定。重新处理时应说明规范版本变化和差异，不静默改写历史解释。

### 来源批次登记

来源批次只登记同时接收或归档的一组资产，用于清单、完整性、位置和处理进度；它不判断逻辑数据集角色，也不提出知识更新。使用 `source-batch` 模板，处理状态限定为：

- `pending-ingest`：仅登记，尚未摄取；
- `in-progress`：正在拆分逻辑数据集或处理；
- `completed`：批次中应处理资产已完成登记的处理目标；
- `superseded`：批次登记已被替代但仍保留追溯。

来源批次与来源笔记不得混为同一状态模型。来源笔记使用 `review_status`，来源批次使用 `processing_status`。

## 4. 对象和主题知识

### 对象笔记

对象笔记保存：

- 身份和别名；
- 当前有效视图；
- 信息性质分层；
- 关系；
- 历史事件；
- 开放事项；
- 冲突和待核验项；
- 来源链接；
- 人工备注。

人工备注和生成区必须分离。重建生成区不得覆盖人工内容。

YAML frontmatter 只保留用于身份、筛选、时间、范围、状态和生命周期的少量字段；叙述、证据、冲突和历史保留在 Markdown 正文。

### 主题知识

主题知识用于没有单一稳定主体、但需要跨任务复用的概念、规则、方法或解释。若某主题开始具有独立身份、状态、关系和历史，再提升为对象。

## 5. 变更建议与任务

变更建议以一次处理批次或一个明确目标为单位。每项建议具有独立状态：`proposed`、`approved`、`rejected`、`applied` 或 `superseded`。

需要人工核验、补充来源、解决身份冲突或执行后续工作的内容，进入任务目录。关闭任务时记录完成证据，不只修改状态文本。

## 6. 上下文包

上下文包必须绑定：

- `purpose`：任务目标；
- `scope`：目标和适用范围；
- `as_of`：时间基准；
- `knowledge_baseline`：使用的知识版本或处理基准；
- `recipe`：若将生成产物，指定 Recipe；
- `sources`：最小充分来源。
- `classification` 和 `access_scope`：继承的敏感性与允许消费范围。

检索顺序：精确目标 → 当前状态 → 直接关系 → 相关历史 → 未关闭事项 → 适用主题 → 冲突和缺口 → 来源。

上下文包不得：

- 无目的复制完整对象历史；
- 混入未批准变更而不标注；
- 丢失时间基准；
- 将推断表述为事实；
- 包含与任务无决策价值的信息。
- 降低来源或知识层已经声明的访问限制。

## 7. 产物生命周期

```text
draft → reviewed → final → archived
```

- `draft`：位于 `40-Outputs/drafts/`，可重复生成，不可作为最终依据。
- `reviewed`：事实、结构或表述已经审核，但可能仍等待批准或发布。
- `final`：明确批准，后续修订产生新版本，不覆盖旧版本。
- `archived`：移动到 `90-Archive/outputs/`，停止当前使用但保留追溯。

`reviewed` 和 `final` 产物必须通过 manifest 保存追溯。每个受控产物目录包含一个 `manifest.yaml` 以及一个或多个交付文件。manifest 记录目标、上下文包、Recipe、知识基准、来源、生成时间、审核状态和版本。

## 8. 保留与归档

- 原始来源按授权和保留策略处理。
- 来源笔记和最终产物默认保留其追溯链。
- 规范化中间数据和上下文包按复现价值、敏感性和成本决定保留期。
- 归档不得破坏链接；必要时使用稳定标识而不是易变路径作为引用补充。
- 删除必须有明确授权、精确目标和恢复或不可恢复说明。
