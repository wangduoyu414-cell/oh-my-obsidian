# Validator 契约

Validator 提供可复现的质量门。它检查明确规则，不替代开放式语义判断。

## Validator 类型

- 结构校验：必需文件、目录、字段、命名和状态存在；
- 语义完整性：主体、时间、范围、来源和信息性质完整；
- 身份校验：重复对象、冲突标识和未确认匹配；
- 合并校验：更新是否遵守谓词级权威性、时间和范围；
- 追溯校验：知识、上下文和产物是否能回到来源；
- 消费校验：上下文包是否越界、过量或混入未批准内容；
- 产物校验：是否符合 Recipe、Template 和生命周期；
- 工作区校验：项目结构和核心 Skill 是否完整一致。

## 设计要求

每个 Validator 应说明：

- 输入；
- 前置条件；
- 检查规则；
- 错误、警告和信息级别；
- 退出码或结果结构；
- 可接受例外；
- 修复责任边界。

Validator 不得为了通过而修改事实、降低验收标准或隐式接受冲突。自动修复只能用于确定、可逆、无语义歧义的问题，并应记录修改内容。

通用 Validator 只能校验跨场景稳定的结构前提，例如必需元数据、状态、来源绑定和 manifest。谓词级来源权威性、身份组合、允许值和合并正确性必须由具体 Schema 配套 Validator 实现；在尚无具体 Schema 时，不得伪造“语义校验已全面自动化”的结论。

## 使用规则

- 在相关阶段尽早运行局部 Validator；
- 最终交付前运行全局相关 Validator；
- 记录实际执行结果；
- 未运行的检查不得报告为通过；
- Validator 失败时先判断是数据问题、规则问题还是实现问题，不盲目修改生产内容。
- 每个具体 Schema 在允许自动应用变更前，必须提供与其权威性和合并规则对应的 Validator。

## 新 Validator 的充分理由

当出现可明确表达、可重复执行且错误代价值得自动检查的新质量要求时新增。一次性人工审阅偏好不必固化为 Validator。
